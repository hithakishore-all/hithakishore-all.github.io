Agent marketplace · B2B platform

Meridian

Every agent, governed and paid for in one place.

Meridian is a B2B marketplace where companies discover, buy, govern and run third-party AI agents, and where the marketplace team proves those agents get used. Partners list one MCP-style tool server. Buyers run it in chat, next to their data or in Slack, and every call passes one policy gateway that checks who is asking, what they may touch and what it costs.

What's real in this prototype

A personal prototype: my own idea, designed and built independently to explore it. Here is what it actually does, and what it simulates.

  • BuiltA web console, a policy gateway (groups, tools, PII masking, spend cap), an agent flow, metering that never bills a retried request twice, owner-only approvals and a Slack bot
  • BuiltFive working featured agents, which are my own prototypes (GTM Orbit, Conviction AI, Credit Simulator, Fieldwise, Readaroo). Every other listing is a sample
  • ScriptedAnswers are assembled from cited demo facts, not a live model, unless Cortex is switched on
  • SyntheticEvery company, person, listing and number, including the operator health metrics
  • Not builtSign-in. The live Snowflake store is written, but the automated test runs offline

01Problem and opportunity

Agents are arriving faster than companies can trust, buy or adopt them. Every marketplace is making agents easier to buy; few make them safe to switch on.

  • 40%of enterprise apps predicted to integrate task-specific AI agents by the end of 2026, up from under 5%Public source Gartner, Aug 2025
  • 19.7%of 750 tech leaders say all their agents are fully secured and governed before going live. 7.2% have a named person accountable for agent behaviorPublic source Gravitee, 2026
  • 53.9 daysaverage time for a new software purchase in Q3 2026Public source Vertice, Q3 2026

The opportunity

Make agents safe to switch on (one policy, enforced everywhere) and make adoption, not bookings, the metric.

02Target users

  • Buyer (procurement)Finds an agent by the job to be done and buys on commitment.
  • IT adminSets groups, tools, write approval, PII masking and a spend cap once.
  • EmployeeRuns agents in chat, next to their data or in Slack, and approves their own writes.
  • Partner and operatorPartners submit agents for automated review; operators watch adoption and supply gaps.

03Product concept and thesis

Approve once, run anywhere. One policy, set by IT, is enforced on every surface where the agent runs.

  • Every fact is cited with a source, a date and an evidence ID, and uncited claims are rejected.
  • People approve writes. Any tool that changes a record waits for the person who asked.
  • Missing means unknown. Stale sources are flagged, never hidden.
  • Measure use, not bookings. The north star is purchase-to-weekly-active.

04User journey and workflow

  1. Catalog: search by the job you need done. Some listings show stale-data or “SOC 2: Not provided” badges.
  2. Buy and deploy: buy GTM Orbit as Marcus (procurement), then set the policy and approve deployment as Priya (IT).
  3. Run an agent: each result shows the gateway trace, every claim with its evidence ID, warnings and cost. The Conviction memo has “Halden will be profitable by 2027” rejected for having no source.
  4. Approvals: a write waits for the person who asked. Approving as someone else is refused.
  5. Review queue: a submission fails the prompt-injection suite, and an update that adds a write scope requires re-consent.
  6. Health: purchase-to-weekly-active, bought-but-unused listings, supply gaps and data freshness.

05Architecture and integrations

Web consoleSlack→Policy gateway→DiscoverResearchComposeValidate→Metering + auditOwner approvals

Every call from every surface passes the gateway first. Agents read only a governed facts view in Snowflake, and calls, approvals and audit entries are written to operational tables.

Built with: Snowflake · Slack bot · Node.js · MCP-style tool servers. Full architecture notes are in the repository.

06Important decisions and trade-offs

  • One policy, every surfaceIT approves once, and chat, the data cloud and Slack all obey the same rules.A central gateway that every surface must route through.
  • Writes wait for the requesterApproving only records the action; nothing leaves Meridian.An extra step for users, in exchange for accountability.
  • North star: purchase-to-weekly-activeBookings hide agents that were bought and abandoned.A harder number to grow, and a more honest one.
  • Automated partner reviewSubmissions run a prompt-injection suite, and new write scopes need re-consent.Slower listing for partners.

07Evaluation and success metrics

North star Proposed

Purchase to weekly active: the share of purchased agents that become weekly-active, rather than bookings.

Verified today Measured

  • An offline smoke test walks search, refusals before deployment, purchase, policy, a cited run with a stale warning, replay without double billing, a blocked group, validator rejection, owner-only approval, spend cap, review rules, health metrics and the audit log
Proposed pilot metrics
  • Proposed Bought-but-unused listings
  • Proposed Time from purchase to first governed run
  • Proposed Policy refusals by reason, as a signal of misconfiguration
  • Proposed Partner submissions blocked by automated review

08Business value

Hypothesis This is the value expected if a pilot confirms the north star. None of it is a measured outcome.

  • For buyers: agents IT can actually approve, with one policy instead of one per tool.
  • For the marketplace: revenue that sticks, because adoption is measured and acted on.
  • For partners: a clear bar for listing, and reach on several surfaces from one tool server.
